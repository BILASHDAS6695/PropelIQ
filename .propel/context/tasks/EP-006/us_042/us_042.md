# US-042: Intake Data Structuring & Storage

## Story

**As a** healthcare provider,
**I want** intake data structured and stored in a consistent format,
**So that** I can quickly review patient information before the appointment.

## Details

| Field | Value |
|-------|-------|
| **Epic** | EP-006 |
| **Priority** | High |
| **Story Points** | 3 |
| **MoSCoW** | Must Have |

## Acceptance Criteria

- [ ] Intake responses stored as structured JSONB in IntakeRecord entity
- [ ] Schema: chiefComplaint, symptoms[], medications[], allergies[], medicalHistory[], severity, duration
- [ ] IntakeRecord linked to: patientId, appointmentId, completedAt timestamp
- [ ] Status tracking: Draft, Completed, ReviewedByProvider
- [ ] Provider can mark intake as "Reviewed" (timestamp + providerId)
- [ ] Intake summary view: formatted display of structured data (not raw JSON)
- [ ] Partial intake saved as Draft (patient can resume)
- [ ] Completed intake immutable (no patient edits after submission)
- [ ] Audit log entry on intake completion

## Edge Cases

- Patient completes intake for cancelled appointment → data retained but marked "Orphaned"
- Multiple intake drafts for same appointment → only latest draft active
- Provider reviews incomplete draft → warning "Intake not completed by patient"
